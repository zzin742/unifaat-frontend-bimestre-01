## 1. Paginação

Controles abaixo da lista, com "Anterior", "Próxima" e a página atual em texto.

O estado dos botões vem **direto dos campos que a API devolve**, sem cálculo
próprio:

| Campo da API | Uso |
|---|---|
| `page` | desabilita "Anterior" quando `page <= 1` |
| `next` | desabilita "Próxima" quando vem `null` |
| `total` | exibido junto do número da página |

O `ListUserController` já resolve isso no backend: ele busca `limit + 1`
registros e, se sobrou um a mais, devolve `next = page + 1` e descarta o extra.
Se o professor mudar o tamanho da página, os botões continuam corretos sem
tocar no frontend.

### Onde fica o estado da página

Em uma variável de módulo dentro de `listUserRender.js`:

```js
let currentPage = 1;
export function setCurrentPage(page) { currentPage = page; }
```

Em ES modules, o módulo é avaliado uma única vez e todos os imports enxergam a
mesma instância — o estado sobrevive entre renderizações sem `localStorage`
(proibido) e sem variável global no `window`.

### Troca de página sem recarregar

`pageButtonClickHandler` chama `setCurrentPage()` e depois `listUserRender()`,
que refaz a busca via `userListApi({ page })` e remonta só a lista. Nada de
`location.reload()`.

O número da página de destino viaja numa propriedade do próprio botão
(`targetPage`), no mesmo padrão que o projeto já usava em `liElement.userId`.

## 2. Edição de nome e e-mail

Cada item ganhou um botão **Editar**. Ao clicar, o nome e o e-mail viram inputs
já preenchidos, e aparecem **Salvar** e **Cancelar**.

| Arquivo | Papel |
|---|---|
| `render/userRender.js` | item em modo leitura + botão Editar |
| `render/userEditRender.js` | troca o conteúdo do `<li>` para inputs |
| `listeners/editButtonClickHandler.js` | entra em edição |
| `listeners/saveButtonClickHandler.js` | valida, chama o PUT, atualiza a lista |
| `listeners/cancelButtonClickHandler.js` | volta para leitura sem chamar a API |
| `api/userUpdateApi.js` | `PUT /users/:id` |

### Validação

O enunciado exige não salvar com nome ou e-mail vazio. A checagem usa `trim()`:
sem ele, um campo com espaços passaria como preenchido e o backend gravaria um
espaço em branco.

O erro aparece no próprio item, com `is-invalid` do Bootstrap e uma mensagem
abaixo dos campos.

A validação de cliente **não substitui** a do servidor — o `UpdateUserController`
também devolve 400 sem `name`/`email`. A do cliente é conveniência (evita a
viagem até o servidor), não segurança.

### Respostas de erro tratadas

Lendo o `UpdateUserController`, o PUT pode falhar de três formas, e cada uma
recebe uma mensagem específica em vez de um erro genérico:

| Status | Origem | Mensagem |
|---|---|---|
| 400 | `name` ou `email` ausente | "Nome e e-mail são obrigatórios." |
| 404 | `findByPk` não achou | "Usuário não encontrado. Atualize a lista." |
| 409 | `SequelizeUniqueConstraintError` | "Este e-mail já está em uso." |

### A ordem importa

A lista só é atualizada **depois** que o PUT responde:

```js
await userUpdateApi(liElement.userId, { name, email });
await listUserRender();
```

Atualizar a tela antes mostraria um dado que ainda pode ser recusado — se o
e-mail já existir, a lista exibiria um valor que não foi gravado.

## Decisões que valem explicar

### Botões como filhos diretos do `<li>`

O `deleteButtonClickHandler` que já existia localiza o item com
`event.currentTarget.parentElement`. Agrupar os botões numa `div` — que seria
mais bonito — quebraria aquele handler **sem erro visível**, até alguém tentar
excluir. Os botões novos seguiram o mesmo nível.

### Só um item em edição por vez

Ao abrir a edição de um item, qualquer outro aberto volta para leitura. Com dois
abertos seria possível salvar um por cima do outro sem perceber, e "Cancelar"
ficaria ambíguo.

### Cancelar não chama a API

Os valores originais ficam guardados em `liElement.userData` na renderização.
Cancelar restaura de lá — sem requisição e sem perder a página atual.

### Página vazia após exclusão

Excluir o último item de uma página deixaria a lista vazia com controles
apontando para o nada. Nesse caso o `listUserRender` volta uma página e refaz a
busca.

### O ciclo de imports

`userRender` → `editButtonClickHandler` → `cancelButtonClickHandler` →
`userRender`. É circular, e é inerente: para renderizar em leitura é preciso
saber entrar em edição, e para sair da edição é preciso saber renderizar em
leitura.

Funciona porque em ES modules os bindings são resolvidos na chamada, não na
avaliação do módulo, e nenhuma dessas funções roda no topo do arquivo. Está
comentado no código para quem mexer depois não quebrar sem saber.
